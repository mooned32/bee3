# 004 — belt-compress и belt-hash: проверка по первоисточнику

## Аннотация

В настоящей заметке закрыт вопрос о расхождении, начатом в [1]: сжатие
`belt-compress` и хэширование `belt-hash`, перенесённые для генератора
псевдослучайных чисел по СТБ 34.101.47-2017, теперь проверены и
воспроизводят опубликованные значения. Попутно установлено шесть ошибок
одного класса: правдоподобный код, дающий правдоподобный неверный
результат. Ни одна из них не видна при вычитке.

Ключевые слова: Кузнечик, сжатие, хэширование, проверочные примеры,
неопределённое поведение, транскрипция.

## Введение

Перенос генератора псевдослучайных чисел по СТБ 34.101.47-2017 [2]
опирается на хэш-функцию `belt-hash`, а тот — на `belt-compress`. Обе
функции в Bee3 не были реализованы: ранее переносились только
`belt-block`, `bash-f` и `bash-prg`.

Первая попытка переноса не воспроизвела проверочные примеры. Расхождение
не локализовалось, и работа была остановлена. Настоящая заметка описывает
локализацию.

Метод: реализация строится по тексту стандарта буквально, затем сливается
пошагово с эталонной реализацией Bee2 [3], скомпилированной отдельно.
Сличение выполняется не по результату, а по промежуточным величинам.

## 1 Основная часть

### 1.1 Что установлено

**`belt-compress` воспроизводит таблицу А.8 полностью.** Пункт 6.3.2
СТБ 34.101.31-2020 [4]:

| Величина | Совпадение |
|---|---|
| S (128 бит) | побайтово |
| Y (256 бит) | побайтово |

**`belt-hash` совпадает с эталонной реализацией на 41 длине** сообщения
от 0 до 40 октетов подряд, включая все неполные блоки.

Это снимает вопрос, поставленный в [1]: расхождение было не в понимании
стандарта и не в блочном шифре, а в переносе.

### 1.2 Шесть ошибок одного класса

Все шесть дают правдоподобный результат: верный формат, верная длина,
отсутствие вырожденных значений. Ни одна не обнаруживается вычиткой.

**Ошибка 1 — транскрипция константы.** В начальном состоянии `belt-hash`
записано как `B194BAC8 0A08F53B 16 6D 00 8E 584A5DE4…`. По тексту
стандарта третья группа — `366D008E`, то есть октет `0x36`, а не `0x16`.
Ошибка в одном октете. Проверяется только сверкой с эталоном.

**Ошибка 2 — число блоков целочисленным делением.** Число блоков
вычислялось как `len / 32`. Пункт 7.8.3, шаг 2.4 требует дополнения
последнего блока нулями, то есть числа блоков равного потолку от деления.
При длине, не кратной 32, хвост сообщения не обрабатывался вовсе, а
выход содержал хэш укороченного сообщения.

**Ошибка 3 — сдвиг на ширину типа.** Запись длины в 128-битное слово
выполнялась как

```c
for (i = 0; i < 16; ++i)
    r[i] = (oct)((bits >> (8 * i)) & 0xFF);
```

При `i = 8` выражение `bits >> 64` выходит за ширину типа `size_t`.
Это неопределённое поведение. На `-O2` компилятор подставил значение
повторно, и длина оказывалась записанной дважды:
`r = 0800000000000000 0800000000000000`. Хэш пустого сообщения при этом
оставался верным — ошибка проявлялась только на ненулевых длинах.

Ошибка 3 — самая опасная из шести: она не видна ни в отладчике, ни в
сравнении выходов, и не даёт предупреждения при включённых `-Wall
-Wextra`. Единственная защита — знание о том, что сдвиг за ширину типа
не определён.

**Ошибка 4 — прибавление единицы к каждому октету.** В режиме счётчика
СТБ 34.101.47-2017, п. 6.2, шаг 3.2 задано `s ← s ⊞ ⟨1⟩2ℓ`. Сложение
выполнялось над числом, но единица прибавлялась к каждому из 32 октетов
раздельно, то есть получалось сложение по модулю 256 в каждом октете, а
не сложение 256-битных чисел.

**Ошибка 5 — длина X в проверочном примере.** Таблица В.2 задаёт
`X ∈ {0,1}2ℓn`, то есть 96 октетов при n = 3. При переносе X был принят
за 32 октета, а за S — вторая строка таблицы. Ошибка в том, что длина
проверочных данных не была сверена с определением из п. 6.2.2 до
использования.

**Ошибка 6 — нарушение строгих псевдонимов.** При загрузке состояния
указатель `u32*` приводился к `oct*`. На `-O2` компилятор подставил
вместо данных значения длины; вывод имел верный формат и длину и был
неотличим от настоящего хэша глазом.

### 1.3 Правила, которые из этого следуют

**Правило о сдвигах.** Любое выражение сдвига вправо или влево на
величину, которая может оказаться не меньше ширины беззнакового типа,
запрещено. Граница проверяется сравнением, а не рассуждением.

**Правило о длине проверочных данных.** Длина каждого значения в
проверочном примере сверяется с определением из текста стандарта до того,
как значение используется. Пример: X в таблице В.2 — 96 октетов, потому
что так сказано в п. 6.2.2, а не потому, что столько напечатано.

**Правило об извлечении документов.** Файл проверяется на читаемость, а
не по сигнатуре. Обрыв передачи даёт файл с верной сигнатурой `%PDF` и
негодным содержимым; такой файл проходит проверку по первым четырём
октетам.

**Правило о сличении.** Совпадение с эталоном проверяется по
промежуточным величинам, а не по итоговому значению. Расхождение
итогового значения локализуется плохо; расхождение первого промежуточного
значения — сразу.

### 1.4 Что осталось неподтверждённым

Режим счётчика по п. 6.2 СТБ 34.101.47-2017 не подтверждён. Проверено:
сжатие и хэширование, на которых он построен, воспроизводят и
опубликованные значения, и эталон. Не подтверждено: значение Y таблицы
В.2. Перебор всех 24 способов распределить первые четыре строки таблицы
между K, S и X₁ результата не дал.

Причина не локализована. Возможные: иное распределение строк при
извлечении, либо иная трактовка `1^2ℓ`. Определённо сказать по имеющемуся
тексту нельзя.

## 2 Заключение

**Вывод первый.** Расхождение, начатое в [1], локализовано полностью.
Оно состояло из шести ошибок переноса, а не из непонимания стандарта.
Блочный шифр был исправен.

**Вывод второй.** Ошибки 3 и 6 не дают предупреждений компилятора при
включённых `-Wall -Wextra` и не видны в выводе. Единственная найденная
защита — сличение с эталоном по промежуточным величинам. Это подтверждает
правило [1] и расширяет его: сверка должна быть построчной, а не
итоговой.

**Вывод третий.** Перенос генератора псевдослучайных чисел не завершён.
Часть его основания — `belt-hash` и `belt-compress` — теперь проверена,
режим счётчика нет. Публиковать механизм под именем Bee3 до этого не
следует.
