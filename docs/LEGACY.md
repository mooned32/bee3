# Исключённые из сборки по умолчанию примитивы

Документ фиксирует, что именно не входит в обычную сборку Bee3, **почему**
и **чем заменяется**. Список не является формальностью: каждая позиция
соответствует конкретному модулю сборки, который физически отсутствует
при `BEE3_ENABLE_LEGACY=OFF`, и конкретной строке в
`include/bee3/crypto/legacy/legacy.h`.

Список признан частью проектной документации и не имеет права молча
разъезжаться с содержимым модулей. При изменении состава модулей
правится здесь же.

---

## Как это работает

| Конфигурация | Что происходит |
|---|---|
| `BEE3_STRICT=ON`, `BEE3_ENABLE_LEGACY=OFF` (по умолчанию) | Устаревшие примитивы **не собраны**. Попытка включить `bee3/crypto/legacy/legacy.h` — ошибка компиляции. |
| `BEE3_STRICT=OFF`, `BEE3_ENABLE_LEGACY=OFF` | Устаревшие примитивы не собраны, но функции, помеченные `BEE3_DEPRECATED_SECURITY`, доступны с предупреждением. Режим для поэтапного переноса кода. |
| `BEE3_STRICT=OFF`, `BEE3_ENABLE_LEGACY=ON` | Устаревшие примитивы собраны. Только для переноса с Bee2 и сравнительных испытаний. |

`BEE3_STRICT=ON` вместе с `BEE3_ENABLE_LEGACY=ON` — ошибка конфигурации,
а не конфликт требований: строгая сборка существует ровно затем, чтобы
исключить небезопасные возможности.

---

## 1. Усечение имитовставок

**Что:** `beltMACStepG2`, `beltMACStepV2`, `beltHMACStepG2`,
`beltHMACStepV2`, усекающие варианты `bash*StepG2/V2`, а также AEAD
на их основе.

**Основание.** СТБ 34.101.31-2020, п. 5.4:

> В алгоритме выработки имитовставки и в алгоритмах аутентифицированного
> шифрования данных вычисляется либо проверяется имитовставка
> T ∈ {0,1}^64. Если требуются не все, а n < 64 символов имитовставки,
> то должны использоваться первые n символов.

То есть стандарт **фиксирует максимум 64 бита** и **явно разрешает**
усечение до любой длины, включая один бит. Для сравнения, ГОСТ Р 34.13-2015,
п. 5.6, для шифра «Кузнечик» с блоком 128 бит:

> Параметром режима является длина имитовставки (в битах) 0 < s ≤ n.

То есть 128 бит — верхняя граница. Политика усечения у двух стандартов
одинакова, различается только потолок: 128 против 64.

Практическое следствие: при 64-битном теге достаточно 2^32 попыток
для вероятности подделки 1/2. Общепринятая практика (RFC 8446 для TLS 1.3,
ChaCha20-Poly1305, AES-GCM) — 128 бит.

**Замена:** AEAD с тегом не менее 128 бит. В Bee3 усечение не является
частью API вовсе; функции, помеченные `BEE3_DEPRECATED_SECURITY`,
ломают сборку при `BEE3_STRICT=ON`.

## 2. belt-hash

**Что:** хеш конструкции Меркель–Дамгард с 256-битным состоянием
(СТБ 34.101.31, приложение Д.1).

**Основание.**

- Стойкость к коллизиям ограничена 128 битами независимо от длины выхода:
  удвоение выхода до 512 бит даёт 256 бит, но не больше. Сравните:
  SHA-256 — 128 бит, SHA-512 — 256 бит, SHA3-256 — **256** бит
  при том же выходе, за счёт 512-битной ёмкости sponge.
- Конструкция МД не обеспечивает мультистойкости и устойчивости,
  свойственных sponge.
- Та же линия развития, что у ГОСТ Р 34.11-94, исключённого из применения
  в Российской Федерации.

**Замена:** `bash256` / `bash384` / `bash512` (СТБ 34.101.77).

**Оговорка.** belt-hash остаётся в СТБ 34.101.78 как хеш для уровня
стойкости l = 128 и как хеш PSK по умолчанию в СТБ 34.101.90-2025.
Bee3 реализует его для совместимости, но **не предлагает как примитив
по выбору** и не использует его внутри нового кода.

## 3. ГОСТ Р 34.10-94

**Что:** подпись на кривых с параметрами `1.2.643.2.2.35.0`,
`1.2.643.2.2.35.1/2/3` (наборы A, B, C), `1.2.643.2.9.1.8.1` («КриптоКом»).

**Основание.** ГОСТ Р 34.10-94 вытеснен ГОСТ Р 34.10-2012. Эти параметры
присутствуют в Bee2 (`g12s.c`) исключительно ради тестовых векторов и
совместимости с историческими сертификатами. Как самостоятельный примитив
выбора они не нужны.

**Замена:** ГОСТ Р 34.10-2012 (наборы `paramSetA`/`paramSetC`),
`bign`, а в перспективе — ML-DSA.

---

## 4. ДСТУ 4145-2002

**Что:** подпись на кривых ДСТУ 4145-2002.

**Основание.** Стандарт не является действующим украинским. Реализация
в Bee2 (`dstu.c`, около 1200 строк) поддерживается только ради
исторических документов.

**Замена:** Ed25519 (RFC 8032), ML-DSA (FIPS 204).

---

## 5. belt-pbkdf2

**Что:** упрощённая редакция PBKDF2 из СТБ 34.101.45, приложение Е.

**Основание.**

- Выход фиксированной длины 32 октета; полноценный PBKDF2 из RFC 8018
  допускает произвольный `dkLen`.
- Рекомендация стандарта — `iter >= 10000`. На современной GPU/ASIC-аппаратуре
  это незначительный барьер: PBKDF2-HMAC-SHA256 с 10^5 итерациями
  преодолевается на порядки быстрее, чем Argon2id.
- Функция не имеет стойкости к подбору, обусловленной памятью
  (memory-hardness), то есть плохо защищена и на ASIC, оптимизированном
  под конкретный хеш.

**Замена:** Argon2id или scrypt для паролей. PBKDF2-HMAC-SHA256 — если
жёсткое требование регулятора важнее стойкости.

## 6. belt-sde

**Что:** секторное шифрование в режиме SDE, построенном на WBL
с изменяющимся раундом.

**Основание.** Режим по замыслу требует одноразового ключа на сектор.
Повторное применение ключа разрушает стойкость полностью и без остатка,
а **ошибка не наблюдаема**: результат выглядит корректным. Класс ошибок,
который невозможно обнаружить в эксплуатации.

**Замена:** AEAD — `belt-dwp`/`belt-che` с тегом 128 бит либо `bash-prg-ae`.

---

## 7. belt-wbl

**Что:** шифрование широкого блока как самостоятельный примитив.

**Основание.** WBL не является блочным шифром в смысле PRP и не имеет
документированных гарантий стойкости для самостоятельного использования.
Он существует как внутренний механизм KWP и как основа алгоритма 6.3.3
выработки одноразового ключа подписи.

Дополнительно: на `beltWBL` построен алгоритм 6.3.3 детерминированной
подписи — самодельная конструкция, не соответствующая RFC 6979 и не
имеющая опубликованного обоснования.

**Замена:** HKDF (RFC 5869) для KDF; hedged RFC 6979 для одноразового
ключа; AEAD для сообщений.

## 8. Переменные по времени операции с эллиптическими кривыми

**Что:** `ecMulA`, `ecAddMulA`, `ecMulPreNAF` — скалярное умножение
на произвольную точку методом NAF.

**Основание.** Индексация таблицы предвычислений значением цифры NAF
скаляра плюс ветвление по длине представления:

```c
ecAdd(t, t, ecPrePt(pre[i], digit / 2, ec), ec, stack);   /* адрес = f(секрета) */
if (naf_size[i] < naf_max_size) continue;                  /* ветвление по секрету */
if (digit & 1) { ... }                                     /* ветвление по секрету */
```

Это канал утечки для любого случая, где скаляр секретен, — класс Minerva
и решёточных атак. Сейчас такие функции применяются только на публичных
данных (проверка подписи), и это правильно: в Bee2 **секретный** скаляр
считается комбинаторным методом с масочным отбором таблицы без раннего
выхода (`wwSel`), что константно-временно.

Проблема в другом: наличие таких функций в публичном API — приглашение
к ошибке. Ошибка будет выглядеть безобидно (проверка подписи), пока
не станет каналом извлечения ключа.

**Замена:** комбинаторные методы с масочным отбором таблицы — уже
реализованы и применяются на базовой точке. Переменные по времени функции
не выходят из внутреннего слоя.

## Что НЕ исключено и почему

| Примитив | Решение |
|---|---|
| SHA-256 | Оставлен. Не уязвим, входит в STB 34.101.78 как основной хеш вне AKI/SKI. |
| SHA-1 | Оставлен с оговоркой: STB 34.101.78-2019, п. 8.1.2 допускает его только в расширениях SubjectKeyIdentifier и AuthorityKeyIdentifier, с явным обоснованием в тексте стандарта. Bee3 реализует его **только** для этой роли и не для подписей и не для KDF. |
| 192-битные ключи блочного шифра | Оставлены. Присутствуют в STB 34.101.31 и в NIST (AES-192). |
| Алгоритмы с уровнем стойкости 192 бит (bign-curve384v1, bash384) | Оставлены. Соответствуют NIST P-384 по уровню стойкости. |
| Магма (ГОСТ Р 34.12-2015, 64-битный блок) | Не поддерживается вовсе. 64-битный блок вынуждает ограничивать объём данных величиной порядка границы коллизий; в РФ алгоритм исключён из применения с 1 июня 2024 г. Если нужна совместимость — берётся «Кузнечик» через внешнюю библиотеку. |

---

## Процедура внесения изменений

Приём нового примитива в `BEE3_ENABLE_LEGACY` требует:

1. Записи в `include/bee3/crypto/legacy/legacy.h` с указанием основания.
2. Записи в настоящий документ.
3. Решения о том, чем примитив заменяется.
4. Проверки, что примитив не используется внутри неlegacy-модулей:
   иначе «исключение» перестаёт быть исключением.

Пункт 4 проверяется автоматически: `tools/check_legacy_leaks.py`
разбирает дерево включений и падает, если модуль из
`include/bee3/crypto/legacy/` достижим из обычного public-заголовка.
